| SNES | Snes9x 1.63 | https://github.com/snes9xgit/snes9x | `1bcc369e89f08243e0a462882fb1f3e42e51de3a` | Snes9x licence (non-commercial) |

Both expose the libretro interface (`libretro.h`, MIT licensed), which is what our shell talks to.

Note on Mesen: the libretro core is the earlier Mesen line (0.9.9), maintained by the libretro team. The newer Mesen 2 has no libretro interface and is not used here.

## Build and test result

Reproduce with `poc/engine-check/build.sh` (needs an activated Emscripten SDK). Tested with Emscripten 7.0.0 and Node 22.

| | Mesen (NES) | Snes9x (SNES) |
|---|---|---|
| Builds for the browser (WebAssembly) | Yes, unmodified source | Yes, unmodified source |
| Module size (gzip) | 2.4 MB (0.6 MB) | 2.3 MB (0.4 MB) |
| Loads and runs a game, produces video and audio | Yes | Yes |
| Save state: save, run on, restore, same result | Pass | Pass |
| Save state size | 36 KB | 823 KB |
| Speed in Node on the build machine | about 8x real time | about 30x real time |
| Needs threads | No | No |

Limits of this test: it used two tiny self-written test ROMs, run headless in Node. Real games, real browsers and phones have not been tested yet. Speed on a weak phone is unknown; Mesen is the heavier of the two. If NES turns out too slow on some device, FCEUmm or Nestopia are lighter libretro cores and can be swapped in.

## Things the shell must do (found during the test)

- Call `retro_set_environment` before `retro_init`, and the other `retro_set_*` callbacks after `retro_init`. Mesen silently drops video and audio otherwise.
- Mesen refuses to load unless the environment callback answers `GET_SYSTEM_DIRECTORY` (9) and `GET_SAVE_DIRECTORY` (31).
- Mesen requires pixel format XRGB8888; Snes9x uses RGB565. The shell must handle both.
- Mesen wants a file path (`need_fullpath`). Either write the ROM into Emscripten's in-memory file system (done in the test) or answer `GET_GAME_INFO_EXT` with the ROM bytes.
- The makefiles name their output `.bc`, but it is a static archive; link it as `.a` with `--whole-archive`.
- No engine needs threads, so the site does not need cross-origin isolation headers (which GitHub Pages cannot set).

## Licence terms and what they require of us

Mesen, GPL v3:
- We may use and distribute it, including the compiled WebAssembly file.
- Whoever receives the compiled file must be able to get the exact source. We meet this by pinning the commit, building it in the open from this repo, and linking to the source from the app.
- Changes we make to Mesen itself must be published under GPL v3.

Snes9x licence:
- Use, copying, modification and distribution are allowed for non-commercial purposes only. No fee, no bundling with commercial products, no use as promotion for a commercial product.
- The licence text must accompany all copies and derived work.
- The project decision "hobby project, not commercial" (see HANDOFF.md) is a precondition. If that ever changes, Snes9x must be replaced (bsnes, GPL v3, is the alternative).

Combining the two:
- GPL v3 and the Snes9x licence are not compatible inside one program. They must never be linked into the same binary.
- Our design keeps each engine as its own separately built WebAssembly file, loaded at run time through the MIT-licensed libretro interface. This is the same separation RetroArch (GPL v3) and its cores rely on. It is established practice, not a legal guarantee.

Licence for our own code (the shell): open question for the user, see HANDOFF.md. Recommendation: GPL v3 or MIT; both work with the design above.

What the app must contain (tracked as F-011): a licences page naming both engines, their licence texts, and links to the exact source commits and to this repo.

## ROM files

No ROM files in the repo or on the server. Users load their own files, which are read locally in the browser. Tests use self-written test ROMs generated by script.
